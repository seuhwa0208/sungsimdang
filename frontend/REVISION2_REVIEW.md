## 반영 사항

1. 관리자 Q&A 상세의 질문 버튼을 공지사항·자료실과 같은 BaseButton 규격의 `수정` / `삭제`로 변경했습니다. 일반 사용자의 `질문 수정` / `질문 삭제`는 유지합니다.
2. 고장 접수 화면의 별도 `현재 상태 변경` 영역을 제거했습니다. 와이어프레임 순서인 접수 폼 → 현재 자산 정보 → 정비 이력으로 배치했습니다.
3. 대시보드 자전거·시설 관리의 검색 옆 상태 선택을 회원 관리와 동일한 드롭다운 필터로 변경했습니다. `전체`, `이용가능`, `정비중`, `이용불가` 중 선택하며 선택한 상태의 항목만 남고 페이지가 처음으로 돌아갑니다.
4. 공개 타슈·기반시설 현황의 상태 필터를 제거하고 위치 입력을 22개 역 선택으로 변경했습니다. 검색 시 Enum의 위치를 정확히 비교하므로 대전역 선택 시 정부청사역이 섞이지 않습니다.
5. 공개 현황의 상태 표시, 전체/상태별 수량과 요약 카드를 제거했습니다. 이용가능한 자전거·시설만 표시합니다. 관리자용 정보는 관리 화면에서 확인합니다.
6. 불필요하게 추가했던 공개 시설 상세 링크·라우트·Vue 파일을 삭제했습니다.

## 정비 이력에 대한 정정

기존 백엔드의 저장 로직은 사용자가 설명한 두 경로를 구현하고 있었습니다.

- 이용불가 상태에서 고장 접수: 새 정비중 기록 INSERT + 현재 상태를 정비중으로 변경.
- 정비중 상태에서 정비 완료: 새 이용가능 기록 INSERT + 현재 상태를 이용가능으로 변경. 앞선 정비중 기록은 보존.

일반적인 이용가능 ↔ 이용불가 변경마다 정비 이력을 기록하는 요구사항으로 해석했던 것은 잘못이었습니다. Service, Controller, Entity, DB 제약은 변경하지 않았습니다.

표시 문제는 이력 응답 DTO에 자산 식별자가 없는 상태에서 프런트엔드가 특정 자산의 이력을 구분할 수 없었던 데 있었습니다. 다음 두 DTO에 기존 연관관계의 ID를 추가했습니다.

- `BikeMaintenanceResponse`: `bikeId`
- `FacilityMaintenanceResponse`: `facilityId`

Mock 응답에도 동일한 식별자를 전달하도록 맞췄습니다. 프런트엔드의 기존 필터가 이제 해당 자산의 기록만 정확히 표시합니다. 정비중 → 이용가능은 기존 완료 API인 `PATCH /api/bike/{id}/status` 또는 `PATCH /api/facilities/{id}/status`를 호출합니다.

새 고장 유형, 상태, 임의의 이력 저장 방식, DB 스키마 변경은 추가하지 않았습니다. 현재 Request DTO에 없는 자유 입력 내용 필드는 새로 만들지 않았습니다.
