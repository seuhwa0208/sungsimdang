## 실제 백엔드와 일치시킨 동작

- 공개 자전거 목록: `GET /api/bike/member/` — 끝의 `/` 필수. 생략하면 현재 서버에서 `member`를 Long id로 변환하려다 400이 발생합니다.
- 공개 시설 목록: `GET /api/facilities/member`.
- 자전거 등록/위치 수정: `{ location: 'DAEJEON' }`. 위치 선택 옵션의 객체 자체를 보내던 문제를 수정했습니다.
- 시설 등록/수정: `{ location, facilityType }`. 존재하지 않는 `facilityNo` 표시를 없애고 서버 id를 사용합니다.
- 상태 변경: `PATCH /api/bike/{id}/maintenance { status }`, `PATCH /api/facilities/{id}/maintenance { facilityStatus }`.
- 고장 접수: `POST .../{id}/maintenance { faultType }`. 현재 Service는 `UNAVAILABLE`에서만 접수를 허용하고 `REPAIRING` 이력을 생성합니다.
- 정비 완료: `PATCH /api/bike/{id}/status`, `PATCH /api/facilities/{id}/status`. 본문 없이 호출하고 새 `AVAILABLE` 이력을 보존합니다. 일반 상태 변경 API로 완료를 우회하지 않습니다.
- `REPAIRING`으로 직접 전환하는 UI는 고장 접수로 안내합니다. 현재 상태를 그대로 유지하는 선택은 허용합니다.
- 회원 탈퇴: `POST /api/members/inactive`, body 없음. 실제 서버에서 검증하지 않는 비밀번호 재확인 UI를 제거했습니다.
- 아이디 중복확인 전용 API는 현재 없으므로 호출을 제거했습니다. 가입 요청에서 서버가 중복을 검증합니다.
- 질문 수정은 현재 Service상 답변 완료 후에도 본인/관리자에게 허용됩니다. 과거 프런트엔드의 WAITING 제한을 제거했습니다.
- 로그인/변경/삭제 뒤 200·204의 빈 본문을 실패로 오해하던 처리를 수정했습니다.
- 위치 Enum은 서버와 동일하게 유지하고 화면에서는 한글 역명으로 표시합니다. 고장 Enum의 `HANDEL`도 서버 원문을 유지합니다.

## 백엔드 보완이 필요한 사항

### 1. CSRF 토큰 제공과 API 오류 응답

`SpringSecurity`는 CSRF를 비활성화하지 않았으므로 기본 보호가 적용됩니다. 현재 토큰 조회 Controller, XSRF 쿠키 발급 설정, 토큰을 담은 로그인 HTML이 없습니다. `/api/csrf`, `/login`의 GET도 현재 서버에서 404입니다.

실제 서버에 존재하지 않는 테스트 아이디로 로그인 요청을 보냈을 때, 보안 오류 처리 과정에서 `/error/403` 리소스가 없어 최종 404가 반환되는 현상을 확인했습니다. 따라서 실제 로그인 및 인증을 필요로 하는 등록·수정·삭제의 종단 간 성공은 검증하지 못했습니다. 보안을 해제하거나 없는 경로를 호출하는 방식으로 덮지 않았습니다.

권장 보완: 백엔드 팀에서 CSRF 토큰을 안전하게 노출할 방식(토큰 조회 API 또는 적절한 쿠키 방식)을 하나 정하고, JSON API의 접근 거절은 403 JSON으로 반환하도록 구성하십시오. 토큰 API 방식이면 프런트엔드의 최초 쓰기 및 세션 변경 이후 토큰 갱신도 함께 연결해야 합니다. 현재 Axios는 기존 `withCredentials`, `XSRF-TOKEN` / `X-XSRF-TOKEN` 설정을 유지합니다. 쿠키가 없다는 사실은 CSRF 비활성화를 뜻하지 않습니다.

### 2. 개별 자산의 정비 이력 식별 정보

`BikeMaintenanceResponse`에는 `bikeId`, `FacilityMaintenanceResponse`에는 `facilityId`가 없습니다. 전체 이력 조회 API만 있으므로 어떤 자산의 기록인지 프런트엔드에서 알 수 없습니다.

이전 프런트엔드는 식별자가 없으면 전체 이력을 특정 자산의 기록인 것처럼 표시할 수 있었습니다. 이제 비어 있지 않은 응답에 식별자가 없으면 개별 이력을 표시하지 않고 조회 제한을 안내합니다. 다른 자산의 기록을 섞거나 이를 근거로 최근 점검일을 만들지 않습니다.

권장 보완: 각 DTO에 해당 자산의 id를 추가하거나, 권한 검증이 있는 자산별 이력 조회 API를 제공하십시오. 현재 프런트엔드는 `bikeId`/`facilityId`가 제공되면 정확히 필터링할 수 있습니다.

### 3. 업무 예외와 세션 권한

현재 Service의 `IllegalArgumentException`/`IllegalStateException`을 API용 400·403·404·409로 변환하는 전역 처리기가 없습니다. 입력/권한/상태 충돌이 500으로 나타날 수 있으므로 `@RestControllerAdvice`에서 구분하는 편이 좋습니다.

`LoginSession`은 로그인 시 Member 객체를 세션에 보관하고 그 객체의 role로 권한을 검사합니다. 다른 요청에서 권한·상태를 바꾼 뒤 이미 로그인된 세션에 반영되는 처리는 코드에서 확인되지 않습니다. 계정 정지/권한 변경 시 세션 갱신·무효화 또는 최신 회원 정보 재검증을 백엔드 팀에서 검토해야 합니다.

### 4. 저장소 설정의 인증정보

프로젝트 `.git/config`의 원격 URL에 인증 토큰이 평문으로 포함되어 있습니다. 토큰 값을 이 문서에는 기록하지 않았습니다. 해당 토큰을 폐기·재발급하고 자격 증명 관리자를 사용하는 것이 필요합니다. 이번 작업에서는 저장소 인증 설정을 변경하지 않았습니다.

## 와이어프레임에서 달리 처리한 부분

- 자전거 번호는 별도 가상 DB 필드를 만들지 않고 실제 `id`를 사용합니다. `Bike-8` 등은 화면용 표현입니다.
- 자전거 그림은 첨부 `.fig`의 원본 이미지를 재사용한 공통 안내 일러스트입니다.
- 대여/반납 API가 없으므로 작동하는 것처럼 보이는 대여 버튼을 제공하지 않습니다.
- 최근 점검일은 공개 자전거 DTO에 없으므로 공개 상세 패널에서 만들어 내지 않습니다.
- 시설 상태는 `AVAILABLE=정상`, `REPAIRING=정비중`, `UNAVAILABLE=운영중지`로 맞췄습니다. 구 와이어프레임의 점검 예정·수리 중 표기를 임의로 다른 Enum에 대응시키지 않았습니다.
